# Security and sensitive-data boundaries

Fixture mode is not a production security implementation. Development user/organisation switchers, client-side repositories and fixture capability checks demonstrate behaviour but provide no authentication or durable tenant protection. Supabase mode establishes a hosted development trust boundary but does not make the unfinished product production-ready.

Production requires identity, MFA policy, secure sessions, server-side authorisation, database row-level security, encryption, audit retention, monitoring, rate limits, privacy review and operational runbooks.

Milestones 4A–4F use invite-only Supabase Auth, cookie-backed sessions, server user verification, relational organisation membership and capability records, and RLS on every application table. Anonymous access is denied. Active membership and capability helpers use `auth.uid()`, fixed empty `search_path` functions and fully qualified relations. A capability in one organisation provides no access in another. Ordinary authenticated users cannot write membership, position or capability assignments.

The active-brokerage cookie is not authority. The server validates it against current active memberships on every context resolution. Supabase mode never reads fixture business data and configuration errors fail closed. The browser receives only the public URL and publishable key; service-role or secret keys are prohibited.

Milestone 2 continues to avoid sensitive financial assessment data. Lead and client records contain contact, ownership, referral and review-scheduling information. Minimal loan records contain lender name, purpose and dates only. No balances, rates, income, expenses, assets, liabilities, credit information, serviceability inputs, lender recommendations or financial documents are collected.

Consent records and campaign eligibility are operational fixture controls. They do not prove a lawful basis or complete all channel, purpose, withdrawal, suppression, privacy, retention, sender-identification or unsubscribe checks required before outreach. The prototype is not described as legally compliant and does not provide legal advice.

Activity events can only be appended through repository-controlled operations. Hosted triggers reject update and delete attempts, while lead, conversion, Client Book, review and referral operations append activity in the same transaction as the business mutation.

The hosted development schema combines least-privilege grants, RLS and mutation-rejecting triggers for audit events, consent evidence, suppression history, frozen campaign versions, audience snapshots/recipients/reasons, approvals and campaign activity. Ordinary authenticated clients remain read-only at the table layer; controlled workflow changes occur only through narrowly granted operation functions. Draft campaign versions remain fixture-only and will become persistent only through a separately reviewed milestone. These controls protect ordinary authenticated access, not database administrators.

`AI Native Operations` (`fgqgcikmaccjamwocpat`) is an explicitly confirmed development-only environment containing fictional data. Its Supabase main-branch classification may display as `production`, so every hosted command must independently verify the project name and reference. Destructive resets, drops, truncation and recreation are prohibited. Secrets, database passwords and service-role keys are excluded from source, documentation and browser variables; ignored local configuration may contain only what a specific development workflow requires.

The checked-in database tests deliberately split concerns. The 40-assertion hosted REST suite verifies the Auth/PostgREST and RLS boundary. The lead-operation runners cover 47 assertions including independent residue checks; the Client Book suite covers 61 assertions; and the retention runner and CLI counterpart cover 86 assertions. The maintenance and referral suites respectively cover 82 and 43 assertions across their guarded operation surfaces, capability and ownership combinations, rollback and residue. Transaction-wrapped pgTAP remains a schema-level suite and is not reported as executed when Supabase CLI delegates that path to Docker/Podman. Temporary TLS connection details and fictional-user credentials are process inputs only and are never printed or checked in.

Supabase advisors report authenticated security-definer operations as intentional warnings because they are the exposed RPC boundary. Definer rights are required so an atomic function can mutate tables that remain read-only to ordinary clients; every function has fixed empty `search_path`, internal authentication/authorisation and explicit authenticated-only execute grants. `operation_commands` intentionally has RLS with no policies and revoked table privileges because idempotency results and actor bindings are internal, deny-all ledger data. Leaked-password protection remains disabled on this development project and remains a mandatory pre-pilot/production control. Performance findings are informational on the tiny seed; indexes are added only for demonstrated read and relationship paths, with representative-volume review still required.

Duplicate candidates, households, referrals, consent records and review opportunities are always resolved inside the active organisation-scoped `TenantContext`. Capability checks are combined with ownership rules: administrators and support fixtures can assign and manage across the brokerage; broker fixtures manage records assigned to them. Persistent referral operations additionally recheck active membership, mortgage referral capabilities, owner validity, expected versions, command idempotency and tenant relationships inside the database transaction; ordinary direct writes remain denied. Inactive partners are excluded from active selectors but remain available through targeted historical links. Referral attribution is mortgage-owned operational history, not proof of causation, commission or revenue. Fixture-side checks remain behavioural simulations, not security controls.

Shared capabilities and mortgage capabilities are separate typed unions. Membership display positions such as Broker are mortgage profile data, not platform roles. Production adapters must enforce the same organisation, capability and ownership rules server-side; the platform/vertical source boundary is an architectural control, not a security boundary.

Campaign planning treats email and SMS as commercial electronic messages and requires channel status `Recorded`; an address, relationship, preferred channel or absence of an opt-out never creates consent. Active organisation/contact suppression takes precedence over channel suppression, then explicit opt-out, missing or Not recorded consent, purpose eligibility and address validity. Multiple reasons are retained. Consent and suppression are append-only histories resolved by effective time; future entries are ignored and equal effective times resolve deterministically by recorded time then immutable identifier. The same rule now drives persistent lead consent display. The latest effective Lifted suppression neutralises an earlier Active entry for the same scope. Reinstating an opted-out channel requires externally supplied source, effective time, evidence note and explicit confirmation, stored with the actor. These controls only record evidence supplied by a user; the prototype does not request consent or contact the person.

These conservative controls are informed by [ACMA guidance on spam, consent, sender identification and unsubscribe mechanisms](https://www.acma.gov.au/avoid-sending-spam) and [OAIC direct-marketing guidance](https://www.oaic.gov.au/privacy/privacy-guidance-for-organisations-and-government-agencies/organisations/direct-marketing). They are not a substitute for legal review or a production compliance program.

The repository re-evaluates current consent, suppression, contact and vertical opportunity state at preview, submission and approval. Earlier snapshots remain available for audit. Approval must reference the snapshot the user reviewed. If the canonical material audience changes, approval is blocked, a new snapshot and structured change summary are preserved, and the revised snapshot requires a second explicit approval. Approval stores the reviewed and final snapshot references, frozen version, current counts, actor, timestamp and `noDeliveryOccurred`; no messaging adapter, provider credential, queue, schedule, export or delivery state exists.

Consent copied from a lead remains channel-specific and retains its original source and timestamp. The copy records conversion provenance but does not establish a lawful basis, override an opt-out or turn Not recorded into consent.
